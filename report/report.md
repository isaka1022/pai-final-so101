# PAI最終課題 説明資料

アカウント名: `<omnicampus アカウント名>`

## 1. 概要

SO-101 アームに、言葉で指示した pick-and-place をさせた。「赤いキューブをシアンの枠に置いて」のような指示文と俯瞰カメラの画像を VLM（Gemini Robotics-ER）に渡し、掴む点と置く点を画像上の座標で受け取る。その2点を机上の世界座標に直し、逆運動学とスクリプトで把持・運搬・設置を実行する。環境は MuJoCo のシミュレーション。

AI を使っているのは2か所ある。「どれを掴み、どこへ置くか」を決める部分は VLM の推論で、学習はしていない。掴む動作は、逆運動学と状態機械で書いたスクリプト版と、手先カメラの画像から模倣学習したポリシー版の2通りを用意した（工夫点5）。

このレポートの中心は、VLM をつなぐ前の段階で**そもそもキューブを掴み上げられなかった原因を3つ特定して直した**ことにある。

## 2. タスクとシーン

- 机上に 4 cm 角のキューブが3個（赤・緑・青）、色つきの置き場が3個（黄・シアン・黒）
- カメラは2台。真上から見下ろす `top`（VLM への入力）と、正面の `front`（動画用）
- 指示文は自由な文。英語と日本語のどちらでも通ることを確かめた
- 成功の条件: 指示されたキューブが一度持ち上がり、置き場の中心から 3 cm 以内で、グリッパが開いた状態で静止していること。押して滑らせただけ、置き場の上に最初からあるだけでは成功にしない

## 3. システム構成

```
指示文 ─┐
        ├─▶ VLM（Gemini Robotics-ER）─▶ pick / place の2点（画像座標）
俯瞰画像┘                                   │
                                            ▼
                          カメラの位置・向き・画角と、高さが既知の水平面との交点
                                            │
                                            ▼
                                 世界座標（pick → 最寄りのキューブ、place → そのまま）
                                            │
                                            ▼
                    pick-and-place（姿勢込みの逆運動学 ＋ 状態機械）─▶ 動画
```

| ファイル | 役割 |
|---|---|
| `pai_final/scene.xml`, `pai_final/env.py` | シーンと環境。退避動作、成功判定 |
| `pai_final/planner.py` | VLM への問い合わせと、応答の検証つきパース |
| `pai_final/projection.py` | 画像上の点 → 世界座標 |
| `pai_final/skill.py` | pick-and-place の実行 |
| `pai_final/learned.py`, `pai_final/grasp_net.py` | 手先カメラからの把持（デモ収集、ポリシー、閉ループ実行） |
| `pai_final/task.py`, `run.py` | 1エピソードの実行、動画と記録の保存、再生 |

ロボットのモデル、逆運動学、把持の状態機械は、自作の PyPI パッケージ `lerobot_env_so101`（0.4.0）にある。下の3つの修正はこのパッケージに入れたもので、提出リポジトリはそれに依存する。

## 4. 工夫点1: 掴めなかった原因を3つ特定して直した

着手時点では、既存のポリシーが「手を伸ばしてグリッパを閉じる」ところまでしかできず、キューブは一度も持ち上がっていなかった。それにもかかわらず、既存の評価では成功率 1.000 が出ていた。数字のうえでは成功していて、実際には掴めていない状態から、原因を切り分けた。

| 原因 | 何が起きていたか | 修正 |
|---|---|---|
| グリッパの極性が逆 | 「開く」の指令で閉じ、「閉じる」の指令で開いていた。関節は下限側で閉じるのに、対応づけが逆を仮定していた | 対応づけを反転した。観測値の符号も変わるので、破壊的変更として版を上げた |
| 逆運動学が位置しか解かない | 手先の位置は合うが姿勢が制御されず、接近する軸が垂直から約 36° 傾いたままになる。ジョーが縦方向に開き、キューブをまたげない | 接近軸を垂直に保つ拘束を逆運動学に足した |
| 指先がキューブを点でしか支えない | MuJoCo はジョーのメッシュを凸包として衝突させる。指の面が V 字になり、接点が1〜2点しかないので、持ち上げる途中でキューブが回って飛び出す | 指先に箱型の当たり判定を足した |

3つ目の効果は、同じ条件で測って比べた。

| 条件 | 成功 |
|---|---|
| 箱型の当たり判定あり | 200 / 200 |
| 箱型の当たり判定なし | 8 / 200 |

再現（`lerobot_env_so101` のリポジトリで実行）:

```bash
python sim/eval_pick_place.py --episodes 200 --seed 1000
python sim/eval_pick_place.py --episodes 200 --seed 1000 --no-jaw-pads
```

成功率の数字は信用せず、描画した画像でキューブが実際に運ばれていることを毎回目で確かめた。上の「1.000」が掴めていない状態で出ていたためである。

## 5. 工夫点2: VLM の点を深度なしで世界座標に直す

VLM が返すのは画像上の点（`[y, x]`、0〜1000 に正規化）で、ロボットが要るのは机上の座標である。深度カメラは使わず、カメラの位置・向き・画角から視線を求め、高さが分かっている水平面との交点を取った。掴む点はキューブの上面（高さ 4 cm）、置く点は置き場の表面を平面にする。

- 描画画像の色の重心から逆算した位置が、実際のキューブ位置に 5 mm 以内で一致することをテストにしてある（`tests/test_projection.py`）
- 掴む側は、得られた座標に最も近いキューブを対象にする。VLM がキューブの側面を指して数 mm ずれても吸収できる
- 置く側は、VLM の点を**置き場の中心へ丸めずにそのまま**使った。丸めれば必ず成功するが、それでは VLM の指した位置の精度が結果に現れなくなる

## 6. 工夫点3: 俯瞰画像を撮る前に、腕を実際に退避させる

ホーム姿勢のままだと、腕が俯瞰カメラの視野の中央を隠す。撮影の瞬間だけ腕の描画をずらすこともできるが、実機では成り立たない。関節の目標値を補間して物理を進め、腕を横へ振ってから撮り、ホームへ戻してから掴みにいく。退避と復帰でキューブが動かないことをテストにしてある（`tests/test_scene.py`）。

## 7. 工夫点4: API キー無しで同じ動画を再現できる

VLM の応答は呼ぶたびに変わりうるし、採点者が API キーを持っているとは限らない。`run.py` は、指示文と VLM の生の応答を JSON に保存する。`--replay` にその JSON を渡すと、VLM を呼ばずに同じ実行をやり直す。

VLM の応答はそのまま信用せず、`pick` と `place` が1つずつあること、点が2要素で 0〜1000 に収まることを確かめてから使う。満たさなければ実行せずに止める。

## 8. 工夫点5: 手先カメラの画像から把持を模倣学習した

スクリプト版の把持は、シミュレータが持っているキューブの正確な座標を読んで動く。実機にはその座標が無い。そこで、把持と持ち上げの区間だけを、手先カメラの画像（96×96）と関節角6個から行動を出すポリシーに置き換えた。

- VLM の点の上空まではスクリプトで動かし、そこからポリシーが位置を合わせて掴み、持ち上げる。運搬と設置は手先の位置だけで行う。腕を動かしている間、キューブの座標は一度も読まない（`tests/test_learned.py`）
- 教師データは、スクリプト版の把持を自動で 300 回実行して集めた。キューブの位置と、開始位置のずれ（±2 cm、VLM の点の誤差を想定）をランダムにした
- モデルは小さな CNN と MLP で、1ステップ先の行動を回帰する。学習は手元の PC で約 100 秒

学習に使っていない配置での把持成功（200 回）:

| 入力 | 成功 |
|---|---|
| 手先画像 ＋ 関節角 | 190 / 200 |
| 関節角のみ | 15 / 200 |

関節角だけでは 15 回しか成功しないので、ポリシーは画像を見て位置を合わせている。

```bash
python scripts/collect_grasp_demos.py --episodes 300 --seed 0
python scripts/train_grasp_bc.py --epochs 30
python scripts/eval_grasp_policy.py --episodes 200 --seed 30000
python scripts/train_grasp_bc.py --no-image --epochs 30 --out out/learned/policy_noimage.pt
python scripts/eval_grasp_policy.py --policy out/learned/policy_noimage.pt --episodes 200 --seed 30000
```

最初の成功率は 70%（35 / 50）だった。失敗した実行の軌跡を調べ、原因を2つ直した。

| 症状 | 原因 | 修正 |
|---|---|---|
| 掴んだ後、持ち上げずに止まる | ジョーが閉じ切って止まっている状態の画像に、「そのまま待つ」と「持ち上げる」の2通りの教師ラベルが付いていた。回帰はその平均を出し、ほぼ動かない行動になる | 閉じ切った時点のラベルを「持ち上げる」に統一した |
| 閉じながら手が上がり、空振りする | 閉じている最中のデータは全体の約 7% しかなく、直後の「持ち上げる」に引きずられていた | 閉じている最中のデータの損失を 5 倍に重みづけした |

2つ目の修正は、調整用の配置（seed 20000）で選び、上の表の数字は調整に使っていない配置（seed 30000）で1回だけ測った。

## 10. 限界と考察

- **シミュレーションで掴めたことは、実機で掴める根拠にならない。** 指先に足した箱型の当たり判定は、実機のグリッパには無い。実機の指は面で当たるはずだが、摩擦やたわみは測っていない
- **垂直に掴めるのは手前の狭い範囲だけ。** x がおよそ 0.30 m を超えると、グリッパを垂直に保てない。シーンはこの範囲に収めてある
- **VLM の成功率は測っていない。** 上の結果は指示文2つを1回ずつ実行したもので、「何回中何回」という数字ではない。応答は呼ぶたびに変わりうる
- **学習ポリシーは 200 回中 10 回失敗する。** 開始位置のずれは ±2 cm までしか学習していない。対象は 4 cm のキューブだけで、画像はシミュレータの描画である。実機のカメラ画像でそのまま動く根拠は無い
- **色で区別できる物体しか試していない。** 同じ色の物体が複数ある場合や、「左の」「大きい方の」といった指示は試していない
- **置き場に先客がいる場合を扱っていない。** 置き場が埋まっていても、そのまま置きにいく
- モーターの減衰・摩擦の値は測定値ではなく、元のモデルから引き継いだものである

次にやるなら、同じ指示文を数十回実行して VLM の点のばらつきを測ること、関節の軌道を保存して実機で再生し、シミュレーションとの差を見ることの2つである。
